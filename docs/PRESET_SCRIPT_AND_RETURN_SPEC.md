## 1. 最新确认

- 预设分支是较完整、可以实际体验的剧本，不只是身份或开场。用户可能没有完整创作能力；先体验成熟内容，再形成创作灵感；构思时也可匹配相似分支供体验。
- 手机属于玩家这个身份，不使用生硬的“长期目标”作为固定前台标签。底层长短尺度可以保留，前台用自然生活记录表达。
- 统一输入可接受，但识别消息、计划、假设、尝试与实际行为须可靠，不能依赖用户先选模式来补偿。
- 离开时世界有少量相关进展，消息须合理跨日期积累；不把三天记录全部集中一天或统一标刚刚。锁屏按联系人/会话折叠真实消息，重点条目要有打开理由。
- 用户已接受结果、关系变化、机会、身份成长、持续经历与阶段满足这组反馈方向；没有数据证明留存提升。
- 世界内不开放与导演对话改当前分支；导演作为内部调度者保留。

## 2. 完整剧本的内容层次（建议）

最新用户回复：目前只需知道会有预设内容，由相关人员提供；不要求此时选择剧本结构。以下内容层次是接入检查的备选参考，不作为对内容提供者的格式要求，不据此开发编排算法。拿到材料后再共同对齐可见范围、角色和事件如何接入；目前不继续追问按章节或条件编排。

|层次|内容|谁可以看到|
|---|---|---|
|可浏览介绍|玩家身份、氛围、开场处境、主要吸引力、预期体验|准备体验的玩家|
|公开生活背景|主角本来知道的关系、资源、约定、既有经历|该玩家世界的公开投影|
|内部人物|性格、自己的目标、边界、未知立场及知情范围|导演与该角色的合法上下文|
|剧本主线|阶段问题、事件触发条件、相关人物、阻力、选择与可能后果|运行层；玩家经历后逐步获知|
|旁线与关系线|可加入或错过的机会、人物自己的行动及影响|按实际参与与获知来源开放|
|阶段收尾|完成、妥协、失败或改变方向后怎样承接|对应事情实际发生后|

每个重要事件至少准备：为何发生、何时具备条件、哪些人参与、玩家可以尝试什么、不同处理怎样影响局面、哪些信息可见、什么时候结束或失效、后续能接什么。不能把possibleOutcomes文字直接视为已发生结果，也不能将整份幕后剧本交给前端再用折叠隐藏。

初批制作建议用一个完整剧本验证内容与运行，再增加第二个明显不同的场景比较通用性。不用固定NPC回复冒充AI；官方明确编写的剧本是内容资产，角色仍按玩家选择真实运行。社区公开发布仍单独讨论。

### 示例：第一部电影（仅产品构思，未上线）

准备阶段围绕试拍、场地、演员和资金形成压力。试拍现场有不同拍摄处理方式，结果影响团队信任与后续合作。资金阶段可能遇到接受条件、争取别的支持或缩小拍摄规模的机会。用户还可以改变想拍的内容、暂缓、放弃原路线。阶段结束留下作品/合作关系或具体损失，不预定必须获奖，也不在每次成功后立即追加危机。

这仍需完整事件和实际多轮评测，不能把上面三段概述当作已经制作好的成熟剧本。

## 3. 聊天与相似剧本体验

用户表达愿望 → Agent区分现实自述与虚构构思 → 归纳想体验的处境/关系/氛围 → 匹配现有可玩内容 → 简短说明相似点 → 用户选择先体验或继续构思。体验可积累本世界经历，不自动写成现实档案；回来后可讨论喜欢哪些部分、想怎样变化，形成新的创作。

推荐依据可以是身份、关系矛盾、想解决的问题、节奏和氛围；不能只按职业名称匹配。不要告诉玩家匹配到了哪个隐藏反转/秘密结局。若没有适合内容，明确继续构思，不编造“已有同类热门剧本”或虚假热度。

## 4. 手机中的自然表达

长尺度意向可显示为一篇便签中的一句话，例如“想把第一部电影拍出来”。具体待办用“这两天要办的事”：完成试拍、给场地方回电话、问清预算。情况用“现在”：场地只剩一个档期，预算需要重新确认。名称按身份和文风变化，不机械将长期目标/短期任务/当前情况这三个产品分类印在所有手机上。

系统从已发生事情整理的进度不可让用户直接改成完成；用户自由编辑的私人便签仍可编辑。两者在必要的详情中说明来源与可编辑范围，不把系统自动生成内容冒充用户此前亲笔记录。用户可通过真实行为或明确选择放下某件事，事件据此更新记录。

多少个任务、哪些可以同时进行、是否跨现场仍是待定玩法。本批现场CurrentMatter有多事项及来源，不能直接声称长期任务图已实现；不用强制每个世界一个任务或只留三个任务。

|输入|合理识别|不得发生|

|现场：把片段放给大家看，再问摄影师意见|分步行动和当面说话|跳过对方回答替玩家完成下一轮|

## 6. 离开后与锁屏的规则

世界推进、消息投递与锁屏展示是三件事。NPC自己的有依据活动形成事件后，才由知道此事的人发送消息；不能只为凑每日数量编造日常。对三天离开且存在相关持续事情的样例，应生成分布合理的多条来信，并与前后状态一致；不要求每位联系人每天都说话。没有成立的进展可保持安静，不能凭日历过去就制造危机。

例子（构思）：第一天询问试拍版本，第二天告知约好的场地条件变化，第三天就一个仍有效的替代办法联系玩家。第三条能打开新选择，前两条仍是可展开历史。每条发生时间、当前状态和发送者知情来源都保存；不是回来时统一标刚刚。

### 锁屏

- 按实际会话ID与应用分组，不按姓名，防同名/群聊混淆。
- 堆叠卡片显示真实联系人、代表消息原文、真实条数和时间；展开保留历史顺序，逐条进入对应会话。
- 不先slice四条再折叠，必须使用授权未读记录形成分组，加载限制需要说明或分页，不能冒称完整历史。
- 首屏突出仍可参与的进展、未解决问题、相关人物与具体机会。只展示已有消息，不新生成夸张预告，也不把过期危机永远置顶。
- 展开不等于已读；真实打开会话再按既有读取规则处理。新消息进入原堆叠仍能感知，不重复提示旧消息。
- 图片、作品、邀约等必须确有成功资产或已保存事件，不能制造假附件吸引点击。

目前NAR回访有界采样至多三拍，已改善跨较长间隔的发生时刻，但不保证每一天实际发言。当前全局调度额度很小，也不能宣称所有世界全天在线。先完成真实历史折叠；跨日连续未了事情、同一联系人多次但不催促的调度质量，再独立评估，不能通过UI假消息弥补。

本轮代码核对进一步确认：clock.ts的selectSpeaker通过spokenInThisAdvance排除同次补算中已发言人物；因此只有一个相关联系人时，三天补算也至多由他发一拍。这是跨日来信能力缺口，不能声称锁屏堆叠能修复。NAR-02S需在既有三拍成本上限、冷却、真实来源与幂等框架内，评估有新内容/相关未了事情时跨日同角色跟进；不能简单删除排除规则后连续催促。用户没有要求无条件每日一条，也不因此改全局1:1时钟。

世界是否真实1:1仍待讨论；本次不改日期策略，但消息/日历/现场/锁屏必须同一故事时钟，暂停不能偷偷流动。

## 7. 反馈与验收旅程

按已接受方向：结果可见、人物行为改变、机会增加、身份成长、共同经历延续、阶段满足。选择后更新相关内容，不影响无关任务；不靠无限追加困难制造留存。成功必须有事件依据，失败有明确限制与可理解的后续。

验收至少覆盖：无现实资料新玩家体验完整剧本；构思中推荐相似作品再返回构思；同一场景两种处理有不同且合理的后果；三天离开已有未了事情跨日来信；锁屏堆叠展开和点入；过期事件不再催；暂停；无相关事情安静；NPC私有动机不出现在HTTP公开投影；未知调用不自动重付。
