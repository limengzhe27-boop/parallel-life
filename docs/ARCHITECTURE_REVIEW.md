# 架构复核 · 2026-09-22

结论：总体分层方向可继续，但上一版存在真实代码缺陷与未闭合的设计。不能用构建成功或单元测试通过证明产品架构没有问题。

## 已复现并修正的代码问题

|问题|触发及影响|修正|
|---|---|---|
|模型 ID 跨轮冲突|模型第二轮再次输出 message_1 等局部编号，正常回复被整轮拒绝|服务端按事件生成存储 ID，模型 ID 仅用于本轮解析|
|角色权限只在应用层检查|其他内部调用直接提交事件可替另一角色说话|共用领域规则并在最终 reducer 强制检查|
|无回复却标记聊天成功|模型仅返回图片任务或事实变更|聊天提案必须包含合法角色回复，否则整轮拒绝|

三项均先新增测试，在原代码上复现失败，再修正。当前无业务 HTTP 写入口，因此第二项是接入后可能发生的权限缺口，不是已上线的数据泄漏事件。

修复后验证：18 项测试全部通过；19 个源文件边界检查与 TypeScript 检查通过；正式构建通过。此轮没有修改或执行 SQL，没有调用真实模型，没有把后续设计条目宣称为已实现。

|问题|决定|实施门槛|

## 不宜承诺的部分

- 多 Agent 长期一致性、人物自然交流、推荐质量，需要真实模型多轮评测。
- 用户人像在新场景中的一致性，不能只通过网关名称或代码推断。
- 持久化队列、并发重复请求的模型费用控制，尚无实现；内存仓储只保证一次状态提交。
- 真人相遇涉及共享时钟与退出规则；当前只有设计约定，不代表联机已完成。

## 开发顺序调整

保留整体架构，不扩张为微服务。优先完成“通用任务 + 游客会话 + 访谈存储 + 真实文字”，尽早验证参考照片生成。手机 UI 与数据库投影随后围绕同一条可运行链路展开。上述缺口列为阶段验收条件，不带着它们直接接成生产接口。
