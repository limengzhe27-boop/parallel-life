# 内部世界发布后台：第一阶段

2026-10-12。依据用户本轮提供的同事正式材料与最新要求：先建内部后台发布世界，已上架世界所有用户都能独立体验。本文是待开发的实施规划，不表示后台或本轮新剧本已经上线。唯一状态表 DEVELOPMENT.md。此阶段从原 CREATOR-PRO-01 拆出，不取消完整专业后台或其他待办。

## 范围

内部创作者/发布人员可以创建作品、保存草稿、管理人物与开场、选择素材、检查、私有试演、发布和下架。发布后复用“分支”精选目录，玩家直接进入自己的存档。不增加消费者底部入口，不开放所有玩家编辑或发布作品，也不让玩家进入后对话导演来随意重写世界。

第一版只做发布闭环，但不是只有上传 Markdown 与一个发布按钮。作品至少包含可运行的世界起点、角色与开场内容。事件正文可保留完整原稿；发布版本仅包含运行时已支持的规则，不承诺导入任意文字即可完整演绎所有节点。

用户本轮再次明确：先做此后台，编剧未来可能继续沿用现有 Markdown/表格/节点/附件供稿，也可能增加字段。任务节点是可能性，导演可以往相应方向推动，**并非每个节点必然发生**。这优先于旧“专业后台最后顺位”的排期；先规划分工，不让多个Agent自行修改同一契约或数据库。

## 剧情候选而非必经任务

作品中的节点分成：已有历史；当前已发生且需要回应的事；尚未发生、可供导演选择的剧情候选。后者不能预先作为手机待办、角色记忆或完成记录。

每个候选节点至少说明：参与人物与地点；可成立的前置；不应发生的排除条件；创作者希望带出的矛盾/体验；导演如何自然引入；发生后可采取的行动；实际选择和行动对应的后果；冷却、最多次数及何时失效。是否发生由当前状态、玩家行动和导演选择决定，不需要按正文目录依次触发。

例如“医院交叉”需要先存在真实的家庭事件，再确认人物知道消息、当前照护安排，以及玩家是否已经答应另一项陪同安排。符合这些条件时导演可以推动交叉；若玩家没有接受陪同，不能为了完成剧本强行把孩子放到现场。玩家拒绝或绕开候选，也应能进入其他合理机会。角色先知道什么，才能发什么消息；拒绝不一定等于失败。

“大概率”可以表达创作者希望导演更关注哪种机会，不能用来替玩家随机做决定。“一定触发”在本稿中是编辑要求，尚未成为不可违背的运行规则；需要按最新产品要求确认其条件，不自动强制签字、赴约或关系选择。导演选中只是进入提议/安排阶段，不等于已到达、NPC已行动或事项已完成。

候选一旦实际发生，可以有分步进展和完成证据；实际记录的结果再影响后续候选池、人物知情与关系。这沿用现有事件/来源/事务，不再建一套任意AI直接写状态的故事引擎。

## 数据库演进：结构化内容与稳定关系分开

不采用“一句人物描述一个数据库列”，也不让所有原稿塞到一个提示词。

|数据类型|建议保存方式|新增内容时的处理|
|---|---|---|
|世界观、主角、角色人格、公开角色卡、导演倾向、候选节点|有 `schemaVersion` 的结构化 JSONB 文档/修订；长原稿另存私有源材料|增加编辑字段、校验、编译/读取规则及测试；多数新增描述不需增加SQL列|
|作品ID、角色ID、草稿版本、发布版本、状态、发布者/时间、当前上架指针|稳定列、关系表和约束|增加新关系或生命周期能力时使用数据库增量迁移|
|发布素材与角色/场景用途、源修订、可见性|稳定关联与版本化清单|新增素材类型需修改用途/访问规则；不能仅新增一段URL文字|
|导演已选事件、玩家行动、NPC实际行动、消息、承诺、完成、机会与记忆|现有世界事件及投影，保持来源与世界隔离|确有新类型或持久状态时补业务契约、投影及必要迁移，不修改旧历史冒充已发生|
|常被查询/排序/过滤的稳定属性|必要字段/索引或经验证的JSONB索引|有具体查询需求后增加；不为所有未来假设提前建列|

JSONB 能保存新键，不意味着任意未知键都获准发布或被导演使用。原稿层可以完整保留未知信息；编辑扩展区须有名称、类型、长度及可见性限制，默认仅创作者查看。运行合同只消费明确支持的字段，重要但未支持的信息提示未接线；不能静默丢弃或直接混入所有NPC提示词。

新增“喜欢的音乐”通常只需角色内容协议/编辑界面/相关NPC上下文接线。新增“共享库存”则涉及玩家状态、动作结果、查询及并发约束，可能需要新表/列及迁移。新增字段从“可保存”到“可以影响玩法”是两种完成标准。

语义有改变时提高内容schema版本，提供纯转换和验证；旧源稿/正式发布版本保持原样，新格式通过编译适配读取。不存在字段与有默认值不同：未知信息不凭默认值制造性格、财产、关系或旧经历。长稿按人物和当前节点预算读取，不把当前16KB设定上限简单改成无限上下文。

### 已有世界的兼容

第一阶段扩展发布内容层，不批量改写玩家世界。现有四个静态模板可用相同稳定ID和版本登记为“内置来源”，逐条核对旧内容摘要和素材用途；新动态模板复用目录能力。模板迁移不能丢掉旧 `seed/worldId`、消息、时钟、回执、照片及原始快照。

旧存档继续使用原始内容版本；缺少新字段通过有来源的兼容读取，不能拿最新版同名人物补成过去事实。确需补稳定元数据/角色映射时，先dry-run输出精确受影响实例与差异，仅更新确认的元数据，事务/幂等/备份/回滚方案与真实PG负例齐备后再执行。不能因为新后台需要字段，就重写其他世界的故事内容。

后台发新版影响新体验；玩家是否迁移到新版是另一项未来产品策略，本轮不默认执行。原有静态模板下架策略和已有继续入口必须兼容。

## 编辑页面

桌面优先：左侧作品/分区导航，中间编辑，右侧查看公开预览与检查结果。手机端可核对、保存与试演，不强求在窄屏编排复杂节点。

|分区|第一版可操作内容|边界|
|---|---|---|
|作品列表|新建、搜索、草稿/上架/下架、当前版本、继续编辑|作品 ID 稳定；名称不充当关联键|
|世界与主角|标题、封面、简介、体验说明、世界观、玩家身份、当前处境、已发生历史、起点时间/地点|虚构主角不写入玩家现实资料；不把未来计划当历史|
|角色|稳定角色 ID、名字、头像、公开身份、人格背景/动机/言行、关系、初始知情|公开档案与幕后设定分别预览；头像跟角色/发布版本绑定|
|开场手机|历史聊天、当前来信、便签/事项、近期安排、可用地点/现场、可用相册素材|时间错开且匹配故事时间；玩家尚未采取的行动不伪写进历史|
|事件内容|保存作者节点文本；编辑现有引擎支持的前置、阶段、完成依据、后果与后续机会|支持与尚未支持的部分显式分开；第一版不需要任意拖拽编程引擎|
|素材|上传、预览、选封面/角色/场景/剧中照片、来源与用途、缺项提示|工作白板不等于角色形象；私人账号素材不自动变成公共素材|
|试演与发布|保存修订、校验、创建隔离试演、查看结果、发布、下架、发布后继续编辑新版本|试演与公开目录分离；发布精确修订，不能拿旧试演给新改稿背书|

导演第一版采用经过验证的系统默认规则。作品可填写基调、冲突、关注的故事线与调度倾向；完整导演工作流编辑器后续再做。创作者填写的要求仍是内容，不获得绕过权限、时间、知情、完成证据等运行约束的权力。

## 版本与发布流程

作品稳定 ID → 可编辑草稿修订 → 校验与试演 → 不可变发布版本 → 当前上架版本 → 每位玩家独立世界。

1. 导入/粘贴原稿先成为未发布资料，不自动解释为人物姓名、头像或事实。
2. 整理结构字段；重复和相互矛盾的材料显示给创作者处理。AI 辅助抽取是建议，最终保存的正稿由内部人员确认，不自动发布。
3. 保存生成新修订，预览仅输出玩家可看到的开场与人物资料。
4. 校验必填、引用、素材、时间/地点、已发生与未来区分、能力支持范围；硬错误阻止发布。
5. 对确定修订私有试演，保存起点内容及相关素材摘要。试演模型/生图费用单独记录，不在保存/切页时自动调用。
6. 发布一次冻结一个版本，记录操作者、时间、校验和试演依据、内容及素材摘要。修改后的新稿需要重新校验，不能覆盖正式旧版本。
7. 所有用户在精选目录读到安全卡片。开始体验创建独立世界；同命令重复返回原回执，继续入口恢复原存档，不共享角色记忆和玩家消息。
8. 更新版本为新体验提供新起点，旧存档继续绑定原版。下架禁止新的进入，不删除旧存档；恢复上架按显式版本操作。

## 现有实现核查

核查起点是已发布 83f9c11，不将主目录未提交创作页面当成完成后台。

已具备：私有设定草稿、不可变修订、owner 隔离、保存乐观版本和幂等；指定修订的私有试演；官方预设每位玩家独立世界/初始快照/时钟/回执；角色真实模型回合。各自限定验收不能代表完整可玩剧情闭环已验证。

需要补：

1. **内部发布身份**：现有签名访客会话不是员工权限。后台页面、读写接口和发布命令都需要服务端可撤销身份/权限，不能仅隐藏入口或让普通游客自称发布者。
2. **动态内容目录**：当前 OfficialLifeId 和 seed 来源限制四个 ID，list 最多四条，数据库实例表亦有四值约束；目录由静态 server packs 组合。要扩展合法稳定 ID，持久化发布版本与上下架状态，兼容旧实例和回执，不凭增加数组元素伪装后台。
3. **运行内容协议**：现有 LifeSettingContent 仅角色 role/desire/voice 和有限故事线，16KB总预算；entryCue 明确只是编辑意图。试演未消费完整任意任务图，因此需按章节/角色/当前节点编译有界上下文，并连接实际可执行事件。
4. **可变人物与开场数量**：officialGenesis 当前要求六 NPC、三位不同人的三条当前来信、每人有限旧来信。不能为满足固定数量自动编造四个人；放宽为经过验证的有界人数/通知/历史，同时保持引用和时间校验。
5. **版本化发布素材**：现有资产按 owner 与 world/revision 授权。公共模板不能引用某一私有账号的照片链接；需要独立发布素材及用途/可见性，实例化绑定到玩家世界，封面公开与幕后图片可见性分开。
6. **稳定人物映射**：现有官方插画适配包含固定预设/名字/关系匹配，动态作品改名不能串图或使旧世界吃到新设定；用发布版本+角色ID关联。
7. **任务和能力验收**：照片、到账、完成、NPC实际收到、地图到达均应由实际事件/素材证明。不能因脚本写了就标成功。当前真实模型全链仍有待验问题，与本后台任务分开记录。

## 同事供稿的第一个样例

阅读索引见 script-library/urban-relationship/INTAKE.md。该稿能提供多线人物、共同压力与差异后果，但缺四份完整核心人物卡、可发布形象素材、统一正史与可执行条件。附件只有讨论白板和关系图。

不要求同事重新按技术模板写作；后台接收其现有稿，再将故事稿分配到对应内容区并提示缺项。先用非露骨且已核对的一段首轮事件做完整发布验证，其他内容保留草稿。不将成人定位当作所有原文自动合规：原文中的露骨性行为、未成年性相关内容及缺少清醒同意的亲密安排不接入公开生成，成人关系冲突可用非露骨表达保留。

## 发布验收最低线

- 普通玩家无法访问后台原稿/隐藏角色资料或写入发布内容；内部人员撤权后命令不能继续执行。
- 保存能恢复、并发冲突不覆盖他人修改；发布指定版本和素材，重复发布命令不重复发版。
- 更新/下架/恢复不修改玩家现有世界；新增作品不需每次改固定代码枚举。
- 全部用户能从精选进入各自世界；两账号消息、知情、记忆、相册和后果隔离。
- 实际角色形象、身份、历史、通知、地图/现场/事项与发布起点一致；未来事件未提前进入记忆。
- 至少首段完成“参与 → 实际行动/接收 → 结果 → NPC承接 → 下一机会”，失败如实保存且可恢复。
- 部署先核对生产迁移与项目目标，再等待READY并公网验证；导入文件和文档部署不算后台交付。
