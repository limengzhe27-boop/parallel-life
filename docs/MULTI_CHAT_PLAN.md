# 个人向导多聊天：产品规则、开发顺序与验收

日期：2026-10-09。用户已同意支持新建聊天，并要求规划、向现有 Agent 分配任务。本文是实施方案，不是已上线功能说明；状态仅记录于 DEVELOPMENT.md 的 CHAT-SESS-00—06。

## 1. 为什么要改

个人向导目前将一个用户的消息放在一个访谈中。用户可能先聊现实烦恼，再构思导演人生，再考虑海边开店；长期堆在同一个对话中，难以回顾，也会混淆当前构思和照片说明。

目标：多个主题聊天，共享一份“我的”，各自保留讨论进度和人生构思；进入分支后的角色聊天继续独立。新聊天是换话题，不是换账号、清空资料、重建 Agent 或新建世界。

当前实现的可核实依据（此为定位，实施时需重新核对冻结提交）：

- db/migrations/0001_foundation.sql：interviews.owner_id UNIQUE，每个账户只能有一个访谈；消息已有 interview_id 与 owner 复合来源关系。
- src/modules/profile/infrastructure/interview-repository.ts：readWorkspace/get/send/sendStreaming 按 owner 查唯一访谈；读任务和问题已有 interview 作用域。
- src/modules/profile/infrastructure/interview-handler.ts：任务带 interviewId，但 readWorkspace 当前只按 owner；改多个访谈后必须修这一入口，不能只改前端。
- src/contracts/api.ts：InterviewSend 没有显式会话定位；当前照片消息、版本和问题必须完整沿用后扩展，不能失去原幂等保护。
- src/modules/memory/infrastructure/question-repository.ts：问题与屏蔽绑定 interview；新建聊天不能成为绕过用户拒绝主题的方式。
- src/modules/discovery/infrastructure/discovery-repository.ts、discovery-handler.ts 与 db/migrations/0004_discovery.sql：当前发现/构思按 profile 保存一份结果；仅加历史聊天列表仍会让不同聊天的提案互相覆盖。
- src/app/api/v1/profile/export/route.ts：当前只读一个访谈，需覆盖多聊天来源与导出。

## 2. 产品规则

### 2.1 入口和界面

保持底部“聊聊／分支／我的”。聊聊顶部有当前聊天短标题、“新建”和“历史”入口；正文仍以对话为主，不加解释面板、资料卡和重复标题。

新建是一次真正的持久操作，有结果后才进入空聊天；重试不能建出两条。默认“新聊天”；首条发言持久保存后可用有界原文片段作初始标题，用户能改名。首版不额外调用模型给每次聊天命名，不把未经确认的推测当标题。历史列表按更新时间排序，分批读取，只显示标题、时间等必要信息，提供明确的空、加载与失败重试状态。

刷新继续当前聊天；首次升级保留既有聊天，标题可为“之前的聊天”。首次进入新账号仍直接聊天，没有姓名、年龄或生日必填。每个标签页当前选择独立，不能因为另一个标签页切换而把本页发送路由改掉。

首版范围：新建、列表、继续、改名和分聊天输入恢复。不加入硬删除、聊天文件夹、搜索、批量归档或新 Agent 类型。删除与遗忘的关系待单独设计；现有资料更正/遗忘能力不得退化。

### 2.2 哪些共享，哪些隔离

|内容|规则|
|---|---|
|现实基本资料、已记录兴趣/经历/愿望、身边的人|同一用户共享一份“我的”；沿用现有来源、真实性、去重、更正与写入规则。新聊天不改变入档门槛。|
|消息、正在讨论的情境、暂定人物身份、开场与构思|属于当前聊天；不把另一聊天的全部对话、故事假设塞进上下文。|
|本轮问题与回答|只作用于所在聊天的问题；不能把 A 的下一条消息当作 B 的回答。|
|用户拒绝讨论的主题|区分本轮跳过与已明确的主题拒绝；后者在同一用户的新聊天中仍有效，直到用户明确更改。兼容策略由契约审查冻结，不能静默解除旧屏蔽。|
|上传照片的消息与“第一张/第二张/这张”|仅查当前聊天内合适的照片组及来源；另一聊天同名人物不能替代本聊天的照片证据。|
|已入档人物与其授权照片|可以通过“我的”供各聊天按需要使用；同一人物可进入多个人生，实际带入仍沿用创建授权。不能因可检索而自动把所有照片送给模型。|
|正在发送、失败/unknown 的图片、文字、素材ID和command|按聊天保存与恢复，不能被切换后的新草稿覆盖或误发。|
|提案与草案|每个聊天单独保存与回读，多个构思不能互相覆盖；分支列表统一展示已保存的分支。|
|已建立的世界、NPC聊天与世界记忆|仍按世界隔离；新建个人聊天不改变已有世界，不向 NPC 开放私人聊天。|

新聊天可以引用与当前主题有关、允许使用且仍有效的现实资料；事实的来源可以保留其他聊天的消息 ID，但模型本轮抽取必须依据当前聊天的真实用户消息。不得根据全局人物名推断图中是谁。遗忘、撤销和被修正资料不因新建聊天再次进入提示词。

### 2.3 分支衔接

每个聊天可构思多条“如果”，保存来源聊天、真实来源消息和当时采用的依据。换聊天后继续原构思，不能读到最近另一个聊天的结果。

分支创建依然是实际确认与任务执行过程，不把 Agent 的台词当作创建成功。各聊天得到的分支都汇入“分支”页；进入手机、回到外层、已有世界及照片授权规则不变。不能迁移时改写已生成的世界或丢掉原草案引用。

全局 discovery 当前会覆盖上一批结果，这是本次必修点，不是等 UI 上线后再打补丁。实施者先确定旧全局记录如何成为稳定历史记录、如何按聊天建立后续结果；不修改已执行迁移，不在本方案提前抢占下一个迁移编号。

## 3. 执行顺序与协作

业务发布顺序：照片模块当前反例修复并验收上线 → 已开发的手机首页集成上线 → 多聊天契约和服务端 → 分聊天构思 → 多聊天界面 → 完整公网验收。

多聊天的只读影响审查可以现在进行，不占照片业务文件。真实视觉输入、手机前史、地图/出行等旧任务保留原编号，不在本批偷偷实现，也不宣称已被多聊天任务取代。图片能上传、关联人物不等于模型已经读取像素。

|任务|主负责人|产出与开始条件|
|---|---|---|
|CHAT-SESS-00 规则与任务链|根协调|本方案、主表登记、发送现有线程指令；仅文档。|
|CHAT-SESS-01 影响与迁移审查|辅助|当前即可在冻结提交只读调查；形成准确文件清单、兼容/迁移方案、验收负例。照片冻结修复的复验优先于本审查。|
|CHAT-SESS-02 公共契约与增量迁移|排查分支创建失败（唯一业务集成人 I）|照片和首页先交付；审查完成后冻结创建/列表/详情/改名、所有权、元数据、旧入口兼容及迁移。|
|CHAT-SESS-03 访谈/记忆/照片按聊天运行|同一 I 串行|所有仓储、流式、后台、问题、来源与客户端公共入口显式定位聊天；真实库及故障验证。|
|CHAT-SESS-04 构思与分支来源隔离|同一 I 串行|提案、草案、种子及任务归属调整，保持旧世界，A/B 构思分别可继续。|
|CHAT-SESS-05 多聊天界面|辅助|稳定契约可用、I 明确停写并释放 interview-app 后，在独立工作树开发；不同时改 client 或公共契约。|
|CHAT-SESS-06 集成、复验与部署|I 集成部署；辅助独立复验；根协调接收|真实完整链、手机/PC、生产迁移核对、READY 与公网验证后才完成。|

有依赖的后续任务先分配负责人，不提前标“进行中”。每项实际开始前登记唯一 Agent ID、冻结提交、文件、数据库和端口；一个业务文件只能一个写入者。辅助不去 I 的数据库、开发服务或构建缓存做并发验证，I 不改辅助专属报告。补充修复也先登记范围，不能绕过照片优先顺序。

## 4. 服务端冻结前必须确认的事项

1. 增量保留旧访谈 ID、消息 ID、人物来源、记忆来源、图片关联、问题与任务回执。旧账号默认聊天不能是“排序最新的聊天”，而应有稳定指向；旧请求不能因为创建新聊天而悄悄变更目标。
2. 创建/列表/读详情/改名全部校验 owner；不靠客户端当前 ID 或 cookie 中某个全局活动会话决定发送目标。旧兼容入口和新显式入口职责需清楚，最终写入还校验 scope。
3. command 的请求摘要包括目标聊天，沿用已有 owner 范围幂等约束；同 command 跨聊天复用必须冲突，不能返回另一个聊天的回执。任务租约、scope、问题 ID 和版本必须匹配。
4. 单聊天流式输入继续互斥；每个聊天的版本独立。多个聊天同时提炼共享资料时沿用保护用户手动修改的乐观锁，不能用慢回复覆盖新资料。冲突结果与未写入资料须如实处理，不假称已记住。
5. 流式请求在开始时锁定所属聊天。用户切到 B 后，A 的 token、metadata、错误及重试仍属于 A；B 不显示 A 回复，也不能因此丢 A 的已持久消息。切换不等于取消已被模型接受的请求，unknown 不能自动重付。
6. A 的照片上传中切到 B，不丢失原图和文字，不拿 B 的输入重试 A。补充说明只读取 A 的照片组；同一资产是否能在两个聊天显式引用，必须按实际授权校验，不能视为已经取消了原保护。
7. 资料检索采用有效、必要且有界的来源；主题拒绝、遗忘和更正过滤在构造上下文前执行，不仅依赖模型听话。聊天的虚构身份不得写入现实档案。
8. discovery、草案回读、basedOn、版本、任务、种子审批和世界创建的来源必须一致；不能改了列表却仍把生成任务入队到另一聊天的当前结果中。
9. 导出应覆盖所有本人聊天及其来源，限量与分页不能静默漏掉旧数据；安全预览、限流、资料容量、模型输入预算保持有效。创建空聊天不调用模型。
10. 如确需新增持久摘要，必须有来源和长度预算；首版可继续使用已有有界历史，不用自动摘要把猜测写成记忆。新功能不要求额外大框架。

## 5. 最低验收矩阵

|场景|必须观察到的结果|
|---|---|
|旧账号升级|原消息、人物、照片、提案与世界仍可回读；继续旧聊天可收到真实回复；默认聊天稳定。|
|新账号|直接聊天；创建后重试/双击仅一个新聊天；列表和改名刷新后真实恢复。|
|跨用户|伪造其他人的聊天、问题、照片或提案 ID 均无法读写；真实库 RLS 和最终仓储入口均验证。|
|A/B 话题|A导演人生、B海边开店分别可继续；B不会自行沿用A的虚构人物身份；允许共享已有效记录的兴趣。|
|不同聊天照片|A两图、B单图；B“第一张/这是小芳”不得绑定A照片；问句、否定、转述仍不得变成归属。|
|上传失败及新草稿|A旧图文失败，B写新草稿，回A重试只送A原图文；不吞B草稿，不重复上传/付费或重发已保存消息。|
|流式中切换|A回应中切B，A回复不出现在B；回A有真实完成/失败/unknown状态，刷新能恢复。|
|问题状态|回答A不关闭B的open问题；同一聊天单open仍互斥；拒绝主题在新聊天继续有效。|
|资料并发/更正|A/B都提炼或用户同时修改生日，慢回合不覆盖用户编辑；重复稳定信息合并来源而非增三条生日。|
|真假身份|A故事职业导演，B现实职业产品实习生；现实字段只按明确现实陈述写入，不被A故事污染。|
|构思隔离|A/B先后推演、回看、修改草案和选方向，彼此不覆盖；分别创建世界，仍正确关联源聊天。|
|重复命令|原聊天重放返原回执；换聊天使用同commandId冲突；不产生双消息、双世界或错误回执。|
|重启/兼容|服务重启及刷新仍恢复；旧入口、已有队列任务和后台handler继续指向原聊天，不随机取第一行。|
|导出/遗忘|多聊天可定位来源；已遗忘内容在新对话提示词中不恢复；不借新建绕过屏蔽。|
|手机/PC|390宽及560短屏、PC居中窄幅，列表/标题/输入/键盘正常；失败提示就近，操作有真实结果。|
|正式公网|迁移 checksum 一致；上线 READY 后用独立合成账号走旧聊天回归及新建→图文→A/B构思→进入世界，不暴露真实私人数据。|

代码交付运行 npm run check 与 npm run build；SQL、权限及队列变更必须补真实 PostgreSQL 集成验收。真实模型验证使用合成经历和自制图片，不上传用户私图做测试。记录失败、重试、可选跳过和当前生产提交；未通过整链不标“可完整体验”。

## 6. 本轮发给现有 Agent 的执行口径

给辅助：先领 CHAT-SESS-01，只读冻结提交并完成影响审查，重点找 owner-only 单访谈假设和全局构思覆盖。仅写自己的报告和状态行。收到照片修复冻结提交时优先复验 PHOTO-QA-03，再回本审查；目前不写多聊天 UI。审查完成后等待 I 契约冻结和文件释放，才领 CHAT-SESS-05。

给 I：继续照片负例和失败重试修复，部署验收后接已交的手机首页；两批完成后按照 CHAT-SESS-02→03→04 执行。先看辅助审查并冻结接口/迁移/文件，不提前占用 UI；向辅助明确交付稳定基线、调用方法、状态事件及文件释放，再集成验收06。不能把新增历史列表当全部多聊天完成。

根协调：保存本方案与任务链、发送消息、收集审查及验收证据。仅文档不占用照片业务文件；不以 Agent 收到消息当作它已完成任务，不把未执行开发或未来上线写成结果。

## 7. CHAT-SESS-01 审查后的冻结补充

辅助已在 eabd025 冻结快照完成只读审查，交付62个影响文件、24组验收场景和5项现有上下文/契约观察。详细证据见 task-reports/CHAT-SESS-01.md；这些观察不是多聊天实现或生产验收。以下纳入开发门槛，代码仍待实施：

1. **分两步上线迁移。** 02先保留原唯一约束，建立稳定默认映射并部署兼容代码；完成03/04的所有显式作用域后才解除单访谈约束并开放新建。不能出现“数据库已有多聊，旧代码按owner取第一行”的窗口。回退保留新聊天数据，用兼容但关闭新建的版本，不能删新聊天恢复旧唯一约束。
2. **基础资料保护并未全覆盖。** 当前人物更新有profile版本检查，基础资料的城市/职业等入口没有等价检查。03需补统一并发保护与明确的未采纳结果；不能称现有行锁已足够。相应故障测试包括慢回应晚于用户手动编辑。
3. **遗忘要过滤同一来源的所有入口。** 当前记忆状态变化不自动使confirmed档案及原始历史退出prompt，需在共享资料检索、当前历史、候选与最终写入采用一致规则。不将记忆遗忘擅自等同删除原文或改写旧世界。
4. **全局人物不全是现实关系。** 照片中性故事标签也会出现在共享people中。需结合来源聊天与来源分类裁剪，不将A的故事标签自动提供给B当现实人物；未知旧标签保留且不提升身份，显式授权跨聊引用仍可支持。
5. **旧历史与不可变记录不能伪造或改写。** 被全局discovery覆盖的旧完整提案本来就不再存在，不能据任务片段重建并标历史原稿；只保存实际存在的记录。已确认草案、seed和初始世界快照禁止UPDATE补来源，使用经过owner/复合FK/RLS校验的附加来源映射，且区分个人聊天与设定试演来源。
6. **元数据和模型回合版本分开。** 改名采用单独metadataVersion，不因改名让生成中回合冲突；导出按所有聊天和消息分页，错误须可见。新增构思聚合若调整任务scope，需连同schema、SQL CHECK、worker注册、租约和旧任务兼容冻结，不能把interviewId塞进名为profileId的字段。

02的完成只代表安全扩展与兼容基线，不能单独宣称多聊天可体验。05可以在冻结契约后开发，但正式开放仍以03/04完整接线和06验收为准。现有照片修复及首页发布顺序不变。
