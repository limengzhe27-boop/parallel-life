# GUIDE / CHAT-PHOTO · 聊天构思与照片归属修复

2026-10-09。依据用户提供的真实体验反例制定。任务状态只见 DEVELOPMENT.md；本文件是验收规格，不是功能已经完成的证明。执行分工为 CHAT-PHOTO-01、GUIDE-02，公共接线、真实调用及发布由当前唯一业务集成人串行完成。

## 1. 用户遇到的问题

用户已经说出想体验的身份、改变的选择、人物姓名和希望逃离的疲惫，向导却反复询问目标、自由是什么、人物关系如何。这没有形成可体验开场，也把剧情策划责任交还用户。用户说“没有特别目标，想更自由”不等于材料不足。

用户连续分享照片、之后再说明第一张和第二张分别是谁。系统默认发送“我分享了一张生活照片”，资料页称“你的生活照片”；现有绑定只接受本轮照片及唯一人物说明，晚到的逐图说明不能关联。模型只收到附图标记，未收到视觉内容，因此不能声称已经看见或识别人脸。

截图里的红色待确认提示在正常上传、消息保存、等待AI过程中出现，按钮同时不可操作。状态误报与上游真正失败需要分开处理。输入框还存在空间拥挤、无法舒适多行输入、发送完成可能清空下一条草稿的问题。

## 2. 产品判断

- 照片默认叫“分享的照片”。没有归属证据时不叫本人生活照、人像、朋友头像或生成作品，不凭图猜姓名、关系、年龄。
- 用户对照片的文字说明是归属依据。支持附图说明，也支持先传图、后逐张说明；运行时找到真实照片消息后才绑定。
- “照片里是谁”“这个人与我现实关系怎样”“他在分支里是什么身份”是三件事。现实资料保留用户实际提供的描述；虚构职务、恋爱关系、未来经历只进入相应创作上下文，不污染现实档案。
- 用户已给身份和愿望时，向导主动提出暂定开场、公开人物安排、眼前一件可做的事。无明确长期目标也可开场，不反复问目标或要求用户写NPC动机、秘密及全部剧情。
- 聊天构思不等于创建成功。创建必须有真实可操作入口、明确用户动作及持久记录；不因AI说“好，我们开始”就伪造分支或开机。
- 不要求先确认全部现实档案才构思虚构人生。只使用用户原话作为创建意向证据，AI自己说出的故事不能触发未经授权创建。

## 3. 照片端到端流程

1. 用户选择图片，上传到本项目私有存储；以实际回执确定素材已保存。
2. 客户端持有该次照片待发送记录和原说明，不重复上传同一已保存素材。
3. 用户照片消息持久保存后，它已发送；AI仍在回复、回复失败、响应不确定，不撤销这条照片消息，不把它重新标为照片没发出去。
4. 晚到说明引用当前访谈内真实用户照片消息。运行时验证同账号、同访谈、消息确实有上传素材、素材可用且未被移除；模型不输出或指定资产ID。
5. 单一照片可按“这张是…”关联；“第一张/第二张”必须存在明确照片组及顺序。有多个候选组或指代冲突时只澄清指代，不随意查全历史第一张，也不再盘问人生目标。
6. 人物记录或创作附件同时留存照片来源和说明来源。重复说明合并来源；相互矛盾的归属不静默覆盖；来源容量不足不能先绑定再丢证据。
7. “我的”按实际用途呈现。聊天分享区中性命名，已关联人物图片展示在对应“我身边的人”；不会同一图片一处称朋友、一处称本人。删除或取消遵循现有真实接口，不删除他人数据、不破坏已有访谈历史。
8. 创建分支时，朋友照片随被选中的人物带入；其角色头像和相册沿用此前产品约定。不得仅因同在共享照片集合中，就自动作为主角形象参考。目标行为：本人头像只来自明确选择，不能让第一张聊天上传自动成为头像。

### 历史接口需要协调的语义

目前 referenceAssetIds 兼作聊天照片的合法引用登记，requireSharedPhoto 依赖它。不能只删除朋友照片的数组项来修复分类，否则已有照片消息会无法引用。当前 includePortrait 的旧种子路径也会带入整组 referenceAssetIds；需要串行复核人物图片排除、本人的明确选择及草案附件范围。保留访问权限登记不代表承诺这些都是本人照片。

2026-10-09进一步核实：profile-repository 的 add-reference-photo 在 portrait 为空时会自动设为该图；delete-reference-photo 删除当前 portrait 时又会自动换成第一张剩余分享图。此前只阅读创建端“portrait引用字段”不足以证明头像是用户明确选择，此判断已纠正。两处自动回退均需一并修复；旧portrait若没有明确用途证据，不应直接认定是用户授权的本人形象，也不批量清除历史，创建默认选择及旧图关联必须明确处理。

现有 sourceMessageIds/sourceQuotes 可以承载照片与说明两种来源，优先复用；若仍需字段，必须由集成人先确定兼容契约和唯一写入范围，不由不同工作树同时改公共契约。

### 用户完整反例中的现实 / 虚构边界

讨论“如果和某人去当古惑仔”之后，再说“第一张是教导主任，第二张是班主任女友”，不能仅因之前出现“如果/古惑仔”就丢掉所有照片声明。声明至少应在当前创作上下文中可追溯地保留，并用于对应人物参考；它本身不能证明现实恋爱或真实违法经历。若无法确认现实关系，使用来源标签或创作附件，必要时仅询问这一项归属，不诱导填写全部现实档案。

只修改称谓、却没有绑定照片或创建时仍带错，不算本项通过。只做视觉识别也无法解决用户声明与虚构身份的区别。

## 4. 照片与回复状态

|实际状态|界面与恢复要求|
|---|---|
|上传中|轻量进度状态，不出现红色失败提示；原说明保留|
|素材已保存，消息发送中|显示发送中；不二次上传、不将本地临时气泡视为服务端确认|
|用户消息已保存，AI回复中|正常等待/流式反馈；照片已发送，清理该次待发送记录，不清空下一条草稿|
|发送结果不确定|先读取原消息/回执；只对未确认部分提供恢复，不自动重付模型任务|
|明确未发送或上传失败|就近错误与能操作的重试/取消；保留素材或本次说明|
|AI失败但照片消息已保存|提示回复失败或未知；照片保留，重试的是回复，不是重复上传图片|

输入可以起草下一条文字，但在版本未稳定时不并发提交新回合。文本框多行增长到上限后内部滚动，支持IME、Shift+Enter、触摸目标、短屏、减少动效；不以模拟短屏冒充真实手机软键盘验证。

## 5. 向导与创建入口

例：用户想体验更自由的身份，已说出人物名但没有目标。向导应具体回应已有信息，提出一个可修改的成年虚构开场和下一件可做的事，而不是继续问“有什么目标”“自由是什么”。这只是产品内容方向，不使用固定台词冒充实际模型回复。

只有真正影响体验边界或照片指代的缺口才提问，每轮至多一个必要问题。暂定开场不能剧透内部秘密或确定所有结局，也不能给现实伤人、勒索等可执行指导。由导演后续安排有后果的冲突，用户仍能选择行动。

创建入口要区分“可以构思”“存在提案”“已有可进入世界”，并复用真实创建链路。用户明确点击后再执行生成/带入/建世界；原有世界可以重新进入。纯照片、寒暄、疲惫、否定创建、模型自行补写故事，不应自动触发创建。

## 6. 必须验证的样例

- 两张不同人的照片连续上传、后补第一/第二归属；人物和素材一一正确，本人参考不混入。
- 附图直接说“这是我表姐”；同图重复说明，不重复人物和模型付费。
- 无归属照片保持中性；头像插画作为头像，不强制图生图或推断真人。
- 原始用户完整古惑仔讨论 + 两张照片 + 后补标签：没有循环追问目标，照片声明没有全局关键词静默吞掉，虚构关系不进入现实事实。
- 多批照片、两人同名、互相矛盾声明、被删/取消/不可用素材：不猜测、不覆盖、不跨访谈或跨用户引用。
- 素材上传成功、消息已保存但流式中断、任务unknown、版本冲突：不重复照片/消息或自动重付；新草稿保留。
- 创建时仅选朋友、仅选本人头像、不选带入，以及旧 includePortrait 路径：实际种子/草案用途符合选择和人物来源。
- 390px手机、PC居中、短屏、长中文、输入法和减少动效；布局样例必须注明是夹具，不冒充真实模型。

执行 check/build；资料与来源/权限/回执变更补独立真实PG测试。真实模型多轮与生产关键流程统一由集成人进行，生产迁移确认后提交推送、等待READY并公开地址验证才算交付。测试数量、单次回复成功、health200都不能替代上述关键验收。

## 7. 交付边界

本批处理聊天引导、照片归属、等待/错误状态及创建入口，不宣称实现图像视觉理解、图生图人物一致性、完整地图旅行或所有长期叙事任务。既有 SCENE-03/TRANSITION-01/NAR-02S 等独立任务继续保留；待验收提交由同一集成人串行合并，不夹带根目录旧私有创作功能改动。
