## 关键问题（9 项）

### 1. P0 图片模板被当成模型生成的写真

- 观察（代码）：`src/server/worker-composition.ts` 构造 `CharacterImageSynthesizer`；`src/modules/media/infrastructure/image-generator.ts` 的 generateAndCommit 仅将 SVG 转 WebP，没有图像模型调用、没有读取参考图像字节，却写入 generated/ready，并在有 referenceAssetId 时绘制“肖像底模已对齐”。`src/features/phone/world-app-data.ts` 将非上传图片描述为 AI 生成写真/事件照片。
- 推断：任务成功与相册可见并不能证明有真实生成或人物一致性。未在公网触发图片任务，不声称本轮复现了某张生产图的生成过程。
- 建议：首先停止把模板输出作为生成成功；占位与真实生成必须具有不同状态/来源。真实模型适配接入原媒体任务、回执和修订流程。
- 验收：真实合成参考图调用证据、图片结果、失败/unknown、刷新恢复、同 requestId 不重复落相册；没有模型结果时不得显示写真已完成。

### 2. P1 创建分支绕过了方向与资料的具体审阅

- 观察（代码）：`src/features/interview/proposal-thread.tsx` 的 create effect 在 discoverBranch 后取首个未使用方向并直接 confirmAndBuild；approveSeed 自动 includePortrait=Boolean(portraitAssetId)、personIds=[]。`branch-intent.ts` 的 CREATE 正则无否定保护，如“不要创建分支”包含可匹配片段。`interview-app.tsx` 在 sendStream 完成前触发 branchCommand。
- 推断：用户谈到创建未必等于选择新生成的第一条方向及授权肖像；新消息尚未入库时读取 workspace，也可能遗漏这次指定的分岔。这不是要求再堆一个确认弹窗，而是当前决策对象不明确。
- 建议：统一聊聊和分支页的创建状态，先给出具体分岔、主角身份、带入资料和照片，再由用户对该版本明确选择；自然语言先转成提案。
- 验收：否定句和询问句不建世界；用户指定的最新方向不丢失；更换方向后授权绑定新版本；无肖像默认带入；每次创建有可回看的起点。

### 3. P1 资料整理有信息隐藏和旧数据分裂

- 观察（公网）：我的页同时存在待确认旧记录、空基本资料、人生经历，用户必须自行理解它们关系。线上一个愿望式“如果当年……”条目被列入人生经历（可能为历史数据，不能据此断言最新 Handler 仍产生它）。
- 观察（代码）：`ProfilePane` 排除所有 identity，而故事列表只渲染 interest/personality/wish；BasicInfo 只读取“个人资料\n”文本块。因此独立 identity、relationship、experience fact 没有完整展示路径；关系人物另在 profile.people。
- 建议：建立统一资料读模型和历史转换策略：基本信息、经历、愿望、重要关系分别可见，来源与修正入口一致。先解决数据映射，再做摘要视觉。
- 验收：每一种已保存事实都有可定位的展示/编辑入口；旧数据升级前后无丢失；假设不呈现为既成经历；一个信息不在多处矛盾出现。

### 4. P1 访谈提示词过早推动想象，欠缺阶段性理解反馈

- 观察（代码）：`interview-planner.ts` 强制每轮描摹平行图景，并以生日/星座作为性格参考；收到照片标记即要求称赞照片，但 context 传入的是文本 JSON，没有图像内容。Welcome 没有年龄生日表单，应保留。
- 推断：容易在尚未理解现实处境时反复“造梦”，让真实烦恼失去承接；星座和未看图却评价照片也损害可信度。并未新发消息验证模型遵循率。
- 建议：对话按已有信息自适应：回应具体处境、追问一个关键未知、适时展示“我理解的你/可探索的分岔”；不固定生日为第一问，不通过出生信息推断性格。图片无视觉输入时只确认收到并询问背景。
- 验收：三类合成经历多轮真实模型评测；无需填生日即可体验；用户想倾诉时不强推创建；推测与用户事实分开；无图像输入时不描述视觉细节。

### 5. P1 基础资料兜底会把经历年份误当生日

- 观察（代码）：`extractBasicInfoFromText` 的年份正则前缀可选、完整日期不要求出生语义；`interview-handler.ts` 将 fallbackBasic 合并后调用 applyBasicInfoInTransaction。因此“2020年毕业”等经历可落入 birthdate 兜底。这里是代码路径判断，未写入线上数据。
- 建议：只在明确本人出生语义及来源下提取，支持年份精度，不把普通日期输入强制成生日；删除猜测式自动覆盖。
- 验收：毕业年份、他人生日、未来假设不改变本人生日；“我是05年的”得到年份精度；用户纠正优先且可追溯。

### 6. P1 进入手机以后缺少可靠的主动生活循环

- 观察（公网）：已有锁屏能显示多角色通知，是可保留的呈现基础；未打开通知以免改变已读状态。
- 观察（代码）：前端 advanceWorld 调用在 director-panel 手动操作；WorldPhoneApp load 读取世界/恢复创建，没有自动推进调度。`advance-world.ts` 已有 agenda/clock/resolveTurn，可复用。
- 推断：开场通知不等于持续生活，用户在手机内等待无法据此获得新的可信事件。本轮没有长时间等待、也未执行推进，不能断言后台所有环境都不存在其他调度。
- 建议：定义进入/回访时的受控推进与未完成事件状态，明确暂停和关键选择停下；复用原事务入口，不能客户端定时插入假消息。其他 NPC 介入仍是候选讨论，不作为本轮实施要求。
- 验收：合成世界在授权的推进触发后产生可追溯事件；重复进入不重复触发；暂停不推进；关键选择等待主角；事件后果跨应用一致。

### 7. P1 准备世界的成功标准与界面承诺不一致

- 观察（代码）：build-repository 的 ready 基于 opening 存在；build-handler 单独创建媒体请求；proposal-thread 却将构筑阶段描述为“微信关系网与图生图身份写真（约30~45s）”，随后按文字任务成功进入手机。
- 推断：玩家会把文字世界 ready 理解成照片也 ready，错误进度放大草率感。
- 建议：主角/关系/开场是可进入条件，照片独立标等待/失败；使用真实阶段和可恢复进度，不靠固定时长承诺。进入时交代“此刻我是谁、发生什么、可做什么”。
- 验收：文字已完成而图片失败仍能进入，明确图片状态；刷新延续同任务；不显示不存在的图生图成功。

### 8. P2 分支列表缺少辨识与决策层级

- 观察（公网390px）：两条同名分支同样描述、不同装饰封面，只显示“进入体验”，难以辨认当前进展；下方又展开三条长篇方向、依据、场景、代价和编辑表单。截图已目视核对。不能仅据同名断言后端重复创建。
- 根因（代码）：BranchList 仅 title/description/status；DiscoveryApp 同页承担已有人生与方向编辑，没有最近事件/时间/分岔差异摘要。
- 建议：分支页优先呈现正在生活的世界和最近变化；新方向采用独立决策层，已有分支增加时间与进展辨识。保留底部“聊聊/分支/我的”。
- 验收：两条同名分支可仅凭卡片区分；首次用户与回访用户主行动明确；手机首屏不被长推荐淹没；PC维持统一窄幅容器。

### 9. P1 资料沉淀结果没有及时反馈到对话

- 观察（代码）：interview-app 的 sendStream 成功仅更新 interview；候选列表在挂载及候选决策后刷新，通常回复完成没有同步 refresh/refreshCandidates。ProposalThread 仍使用旧 profileVersion/confirmedCount；最新 Handler 已有自动整理写档案逻辑。
- 推断：用户聊完看不到刚整理的结果，需刷新或切页面才感知；资料与分支入口易显示过时判断。未发送线上消息验证时序。
- 建议：一次访谈完成统一刷新相关投影，在对话就地提供简短整理反馈和可修改入口；避免把“已理解/已可创建”仅由一条 confirmed fact 判断。
- 验收：回复完成后无需刷新即可看到新增/修正资料；版本冲突不回退；何时可创建依据分岔信息完整度，允许用户明确选择简略起点。

## 最后交叉挑战：EXPERIENCE_REBUILD 复核（2026-09-28）

已只读核对完整方案。优先真实性门槛，再统一资料/草案/事件附件契约，随后整页替换外层与手机，方向正确；但契约统一本身不能保证旧路径退出。以下三项建议是验收补强，不扩张首批功能范围。

1. **把旧路径退出写成每批交付条件，避免契约统一、执行仍分叉。** EXP-03 应同时列出入口→唯一用例→持久对象的对应关系，以及旧组件、接口、样式和数据读法的替换清单。迁移期允许只读兼容适配，不允许新旧创建/授权同时独立写入。EXP-04/05 的开关应切换一条完整路径，回滚只切界面/适配版本，不撤销用户已提交事件。验收：所有入口使用同一草案版本和授权快照；旧入口被删除或转发；保留旧世界的回归样例。EXP-05 可先做界面，但其主动状态验收必须依赖 NAR-02/03；单独页面上线不能算手机生活完成。

2. **主动世界先交付可恢复的调度单元，再接自动触发。** 方案已有正确方向，仍需明确持久触发身份、消费游标、租约、重试及暂停语义；同一到期事项被多标签页/回访/Worker 同时发现时，只产生一组有效后果。时间推进与事件提交不能让失败后跳过未完成事项，媒体晚到也不能向已撤销授权的接收者投递。验收须在真实 PostgreSQL 中注入“取得租约后崩溃、事件提交后通知前崩溃、暂停与提交竞争、离线补算中断”等故障，并证明可续接、不重复、关键选择未代答；不要求恰好一次执行模型，只要求幂等提交和诚实 unknown。

3. **把自由输入的接受标准独立出来，不让新草案流程变成隐形问卷。** 对话状态应允许跳过、回退、更正、换话题、闲聊及直接指定人生；模型提出的草案/行动仍需运行时区分讨论、否定、假设、明确操作。用户可以不按提示回答，不应被正则误建世界，也不应被迫从快捷选项作答。建议用同一组测试语料贯穿聊聊和手机：否定创建、引用他人话、修改已选方向、同时提出多个想法、拒绝邀约但继续聊天、提出新的有效方案。验收观察实际草案/事件变化及来源，而非只检查回复听起来合理。先贯通一个“自由表达→修改草案→进入→主动来信→自由回应有后果→回访”的纵向样例，再扩大三种身份和全页面视觉验收。
