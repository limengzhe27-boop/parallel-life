## 1. 结论与最小实施顺序

先用确定事实打通 **scene.entered → scene.opened → time_place/可选环境叙述 → 玩家可输入**，允许只有玩家的空场景；环境开场不调用 ScenePlanner、不生成任何人的对白或到场决定。已有实际在场人物后，由同一个 `runNpcAgent` 生成各自对白。移动与撤回预约通过注册能力提交真实结果，不能靠环境叙述补成功。

分三步交付，不能把第一步算成全部能力落地：

1. 确定性原生开场、可重放环境事件、真实租约同事务结束任务。无 NPC 时照常可用，保留旧引擎读取与执行隔离。
2. 强类型能力注册与玩家输入分流、NPC 出发/到达、自己发起预约的撤回；结果和空间/日历/知情投影同事务。
3. 可选 SceneEnvironmentAgent 丰富环境。需要独立受保护响应与 unknown 恢复；不可为了环境文案阻断第一步，也不能新增一个类就声称已接通。

## 3. 环境输入、条目与事件的最小契约

以下均为**拟议内部接口**，由 root 冻结后才实现；不是当前已导出的 API。保留现有场景任务输入，避免再造持久队列。

```ts
type SceneEnvironmentInput = {
  worldId: string;
  sceneId: string;
  enteredEventId: string;
  enteredVersion: number;
  expectedWorldVersion: number;
  engineEpoch: number;
  storyAt: string; // 服务端投影世界时钟，非模型填写
  place: { id: string; name: string; description: string; sourceIds: string[] };
  actualPresence: { subject: Participant; positionSourceId: string }[];
  observableFacts: { sourceId: string; text: string }[];
};
type EnvironmentProposal = {
  narration: null | { text: string; sourceIds: string[] };
};
type NativeSceneOpenedData = {
  sceneId: string;
  enteredEventId: string;
  environment: {
    schemaVersion: 1;
    producer: 'deterministic' | 'scene_environment_agent';
    inputHash: string;
    placeId: string;
    storyAt: string;
    entries: SceneEntry[];
    presenceProofs: { subject: Participant; sourceEventId: string; sourceVersion: number }[];
  };
};
```

`SceneEntry[]` 的实际验证必须进一步收窄：恰好一个现有 `time_place`；零或一个 `narration/perspective:observable`；禁止 dialogue/user_action/adjudicated_result/media_reference。ID 由服务端生成稳定合法 UUID，与 sourceEventId/sourceVersion 及事务版本完全一致。文本超限明确失败，不能截断后声称成功。

首版确定性生成：time_place 使用当前已验证 place.name 和 world storyAt；地点 description 有可见作者来源时全文作为可选叙述，没有就不造环境。不要补“无人回应”“门可以随意进入”“某人在等你”“你很紧张”等固定句式。没有人物在场只表示当前没有 NPC 证据，不宣称整个地点客观空无一人。

authoritative player position 为 at 且匹配 scene.placeId，是进入后的空间证据；旧存档缺位置可使用真实进入事件与已保存 world.space.currentPlaceId 对应的玩家位置来源进行受控投影恢复，不能从地点名猜。NPC 仅允许：在开场输入版本之前有权威 at 同地记录；或更早真实 presence 有来源，且之后不存在离开/移动的反证。position in_transit/unknown、contactActorIds、预约 participantIds、导演事件候选、角色说“会来”均不允许加入。

开场同地 NPC 加入 scene 时记录原始位置证明；这只是“该已在当地的角色进入这个会面范围”的投影，不产生新旅行。不能对所有 scene.presence 重盖新位置时间，尤其不能把旧位置证据时间写成当前刚刚到达。真实到达事件才更新到达时刻。

若新世界目前完全没有 NPC 初始实际位置，诚实结果就是暂时没有可证明在场的人；需要作者明确初始位置或经审定的 genesis 位置事件才能建立起点。现有 places.actorKeys/contactActorIds 不可自动升级为这项授权，旧存档也不能从联系人补填。同理，unknown 起点不能凭空 travel.begin。这是后续产品接线依赖，不得用导演一句“让人物出现”掩盖。

可选环境模型只能看到 place 和公开环境 facts，不接 NPC 私聊/动机/导演私有审计，不可改 place/time/presence/预约/事项；提示词不是权限检查。首版允许模型只从有来源环境材料润色，未知天气、路人、门禁状态不可增为事实。将来要允许创造环境事实，必须另设有来源的世界能力，不能藏进 narration。

## 4. 原生开场的任务租约与一个 UoW

拟议服务端入口：`handleSceneEnvironmentTask(lease, signal): Promise<boolean>`。仅在 task.kind=world、epoch>=2、精确 scene task 且 actionId=null 时消费；其他合法渠道返回 false 给对应新处理器。epoch>=2 命中后失败必须显式失败，绝不 fallback 旧 Planner。未知/混合渠道在入口拒绝。

执行流程：

1. 通过现有 `withLeasedAgentDatabase(appDb, lease)` 读取真实任务，检查 owner/world/token/实时租约/input 精确一致/epoch；核 scene.entered 原事件、成功原命令回执、scene 当前 active、玩家仍是 currentScene 且未离开。
2. 读取当前 world CAS 版本、时钟、地点和位置来源，生成不可变 EnvironmentInput 与 hash。**确定性路径没有模型调用、没有必要制造 NPC AgentAttempt。**
3. 同一短 SQL 事务重验租约、原进入证明、epoch、暂停/时间与版本、当前场景、全部入场位置证明；若已离开、切换地点或位置变更，不把过时环境写回。严格版本失效时结束为 conflict，只有显式、无付费的重新准备流程可取新快照，不能暗中解释成原输出仍适用。
4. 写一个原生 `scene.opened` 事件及严格 environment data；reducer 校验事件内容与 world CAS，保存 scene entries/presence 区间、world/command receipt、awareness 与必要 outbox。开场不写预约 attended、不更新事项完成、不执行玩家动作。
5. **同一事务**用独立环境 finalizer 结束实际父任务为 succeeded/resultVersion，并绑定 task input.sceneId、原 enteredEventId、实际 environment event/成功 child command。不能复用要求 actor AgentAttempt 的 `finishNativeAgentTask` 假造 NPC attempt。child command 使用稳定合法 UUID（吸取 44-9 实际入口错误），所有写入失败一起回滚。
6. 只在提交后通过持久 outbox/队列唤醒已经入场且确有输入来源的 NPC；其最终对白仍走 runNpcAgent，各自渠道/隐私裁剪。没有 NPC 时不 enqueue 假人物任务，环境任务也不因零对白失败。

幂等先查原 task/child command 的真实成功回执，确认 hash 与事件/scene 关系后重放，重复 claim/重试不能再插 time_place。租约续期走现有 queue；网络/模型调用不占 SQL。无任何外部动作的确定性失败与付费 unknown 必须区分。

可选模型路径另需受保护 EnvironmentAttempt（不假扮 actor state）：reserved/request_sent/response_received/committed/unknown/stale/invalid/cancelled 等状态、原快照+原响应、token/hash/版本。响应到达后存储成功再 commit；response_received 恢复重用原响应，不付第二次钱、不拿新场景重解释。当前没有此环境存储证据，不能称可选模型已可上线。

replay 必须新增明确环境分支，重放 entries/presence 的同一投影；不能只改 world.version 留 scene_sessions/scene_items 依赖首次副作用。旧 scene.opened/worldResults 读法保留按协议区分。进入历史回放不执行任务、不重新调用环境/NPC。

## 5. 强类型注册能力与结果

当前 AgentAction.parameters 是宽 record；迁移时在注册表按 capability 做严格 discriminated parse，不能因原契约宽而信任模型写的 actorId/outcome/版本/位置。下面是拟议的最小执行载荷：

```ts
type RegisteredAction =
  | { capability: 'actor.travel.begin'; parameters: { routeId: string; toPlaceId: string } }
  | { capability: 'actor.travel.arrive'; parameters: { journeyId: string } }
  | { capability: 'appointment.withdraw'; parameters: { appointmentId: string } };
type CommittedOutput =
  | { kind: 'travel_begun'; journeyId: string; fromPlaceId: string;
      toPlaceId: string; departedAt: string; earliestArrivalAt: string; routeSourceId: string }
  | { kind: 'travel_arrived'; journeyId: string; placeId: string; arrivedAt: string }
  | { kind: 'appointment_withdrawn'; appointmentId: string;
      previousStatus: 'proposed' | 'confirmed'; status: 'cancelled' };
type CapabilityExecution =
  | { status: 'committed'; result: AgentActionResult; output: CommittedOutput }
  | { status: 'waiting'; code: 'NOT_DUE' | 'MISSING_CONDITION' }
  | { status: 'blocked'; code: 'NOT_AUTHORIZED' | 'VERSION_CONFLICT' | 'INVALID_TARGET' }
  | { status: 'unsupported'; code: 'UNREGISTERED_CAPABILITY' | 'MISSING_ROUTE' }
  | { status: 'unknown'; attemptId: string };
```

此类型仅展示新增三种能力，实际 registry 仍保留已经执行的 plan.record/appointment.propose。等待、未支持、不确定都不是成功 AgentActionResult，不能为了满足 outcome 枚举填 succeeded/failed。业务内确认失败可保存失败结果与失败证据；外部结果未知保留 protected attempt，不能自动重做。

参数中的 actorId 一律由当前 runNpc 绑定人物，不从模型参数或 targetIds 接管。执行前先现有 eligibility（来源/当前 goal、plan、责任 revision/玩家决定/依赖结果），再具体能力守卫；每项输出与保存事件、权威位置/日历投影、动作 result/handle/goal 状态都需原子一致。

`handledResponsibilityIds` 与 `completedGoalIds` 只能由执行器按能力语义和实际证据填写。出发成功不等于到达，抵达不等于赴约完成，撤回不等于玩家拒绝，任何一项都不默认完成整个剧情事件。依赖结果的对白仅在对应能力真正提交成功后保留；不能保留无依赖的成功旁白来掩盖执行失败。

### 5.1 actor.travel.begin

- 必须读到本人权威 at 起点，不能从 contact/旧记忆/私聊位置陈述推导。没有本人位置，先缺证据受阻；不能初始化为玩家同地。
- route 必须是该世界已登记、来源可验证、起点匹配、终点合法且本人获准知道的路线。不给全地图，不用 hidden 作者地点补路。已有 `default_travel_v1` 是明确产品策略，不是地理估算；可在产品明确允许且保留策略来源时复用，不能暗中编造其他距离、经纬度或时长。
- CAS 本人位置来源版本；不得同时两条活动 journey。出发时由 kernel 派生 departedAt 与 earliestArrivalAt，不信任模型时间。场景 presence 的离开区间与 position=in_transit、journey、action result/event 同事务提交。
- 用专门的 `actor.travel_begun`（拟议）或带强类型空间 effects 的 Agent native event 记录变化。root 只能选一种规范写法；不同时追加两份重复世界动作。位置不能提前写目的地 at。
- 只有实际在场且具可观察条件者获“离开起点”知识，不自动知道目的地；私聊里声称目的地也只是 report，不升格实际位置。本人知道自己的旅程不授予其他人物读权。

### 5.2 actor.travel.arrive

- 找到同一 NPC 已提交的 active journey，与开始事件、route、位置 in_transit、最新位置版本吻合；不能让模型提交任意 journeyId 或改目的地。
- 用真实世界投影时钟检查到达条件。storyAt 未到 earliestArrivalAt 时 waiting，不能由模型说“已经到了”推进世界时间；暂停/多人生各自时钟沿用现有机制。
- 到达由可靠任务唤醒同一个人物运行时/受控 kernel 完成，无需模型重做物理移动；自动到达必须以已经接受的旅程为授权。先持久调度，禁止 HTTP 后台裸 Promise/setTimeout 冒充执行者。
- 这是已提交旅程的受控延续，不是重新让模型提一个 arrive 计划。当前 eligibility 一般要求 active goal/plan，不能直接套用导致途中目标撤回就永远悬在 in_transit；root 应为已接受 journey 的完成定义专用核验（真实旅程、位置 CAS、时钟、有效取消/改道证据），而非复活旧 goal。未来支持中断/改道时另记真实新动作，不能将 position 直接重置为起点或任意目的地。
- 同事务写 travel_arrived 结果、position=at 目的地、结束 journey；若目的地有当前有效且允许加入的会面，再以真实到达事件为来源添加 presence。单纯到达地点不是强行加入任意私人场景；无会面继续只有位置事实。
- 只让确实目击到达者得到 at 知识，旧地目击者不获目的地。场景看到来人后才唤醒本人与有权限的其他人；不让全员收到 raw 私聊旅程。
- 幂等依据 journey terminal/result/event；重复到达不重复对白、presence、能力结果或唤醒。过期任务/epoch/lease 变化无写入；若本人已经另有真实移动，不能旧任务把人拉回来。

### 5.3 appointment.withdraw

- 不能直接调用以玩家为主体的 InvitationCommand(cancel)，伪装用户决定。能力主体由当前 NPC 身份绑定；来源须从真实提议事件/该能力结果回执证明本人有撤回权，participantIds 包含自己不等于发起者。
- 最小首版只允许撤回本人发起、仍 proposed/confirmed、协议明确可由发起者撤回的预约。未确认/legacy 无发起来源、多参与者只有本人退出权但无全局取消权时，明确 unsupported/not authorized，不能取消所有人的约定。
- 长期完整版本若支持“仅我退出”，须独立参与者承诺投影，保持其他人约定；不能硬塞全局 cancelled。此扩展当前没有完成，不包含最小首版成功承诺。
- 新事件/typed effect 明确 actor 主体和 withdrawal 原因来源，calendar 状态 cancelled；本人责任 withdrawn，撤销相关等待检查，不凭空为玩家加 declined 决定，也不改其他无关目标/预约或真实 presence。
- 对方是否收到取消信息与实际预约状态分开。现有日历向玩家可见时更新手机日历；通知/微信须真实投递事件，NPC 知识只能来自可见日历/实际通知。未送达不写“对方已知”。
- 44-10 外部预约投影目前针对旧 invitation.responded 的玩家 accept/cancel；需要 root 扩展 actor-withdrawn 类型并验证本人与其他责任 revision/观察来源，不能把 actor withdraw 当作玩家 cancel 来复用 decision declined。

## 6. 玩家行动必须单独接通

现有 classifySceneInput 只是保守记录分类，**不是能力执行授权**。玩家输入“去医院/拿到了/检查完了”不直接等于 travel/item-transfer/inspect 成功；原话、意图与结果分开保留。

最小新流程：保存原输入/accepted receipt → 确认可执行操作（已有明确按钮或严格提案待玩家确认）→ 运行当前角色主体为 player 的 registry → 保存实际结果及可观察条目 → 唤醒相关 NPC。自由对话可以不触发物理能力，不强迫所有聊天填写条件表。纯说话可以由已保存 user_action 提供实际发言证据，不能进一步证明对方回答/接受。

player 能力与 NPC 能力分别授权；不能让玩家调用 actor.travel.begin 为他人行动，也不能用 NPC 当前 actionId 携带玩家未选后半步。plan/hypothesis 保持只记录；结果未知/未支持时保留原文并明确告知尚未执行，不能生成“你已经完成”旁白、奖励或事项闭环。超出注册能力的生活动作可以继续讨论/请求，但直到有真实执行规则才写实际结果。

现有原生 NPC reaction 只产本人对白，不负责解决玩家 action；不能仅结束 NPC 父任务就把玩家 scene action 标 resolved。应明确链路中环境观察、玩家能力结果、NPC reply 各自回执，失败恢复不得丢失已经提交的真实发言。

## 7. 旧 R17 专属规则如何迁移而不删掉守卫

保留旧 epoch-1 reader/reducer；新 epoch-2 入口不 import ScenePlanner/scene-step-progress 专属逻辑。每个世界使用已发布作者快照绑定的 `WorldRulePackage`：packageId/version/contentHash/作者 snapshot source、适用世界、注册动作 schema、规则与证据要求；不靠 persona 含“维修”或看到“R17”就全局启用。

R17 是一个已有故事包示例，不是 generic capability：接收/检查可以未来使用通用 item.transfer/inspection.record，但必须先实现物件身份、拥有/转移权、实际同地、对方本人接受、检查对象/结果等真实执行契约。尚无物件库时继续明确仅该包支持，不把常量改名就宣称通用。

现有以下守卫迁移到通用执行器和包证据规则，不能以“去硬编码”为由删除：owner/world/source/版本；否定/引用/历史/未来意向不当当轮执行；玩家与 NPC 主体不混淆；来源引文/动作槽位绑定；当前真实 presence；未作出的后半步不执行；结果只在同事务保存成功；事项条件逐个核验，不因一句台词全部完成。旧正则可以仅用于该包的有限候选识别，不能变成新通用自然语言真值判定器。

历史已保存 R17 结果仍可重放，不重新执行、不改变作者原稿、不回填所有世界规则。新包必须 root 协调内容契约与发布来源；没有 pack 时 generic 环境仍正常开场，只是不执行该专属物理动作。
