# D-17 Phase 1 记忆接线（写入去重 + 用户纠正/遗忘），并修复运行角色函数权限回归

负责人 dsh-main-20260923（主登记目录，单人执行并自审）。2026-09-24。状态：已完成并上线验证。

## 一、记忆写入接线（用户最早的痛点）

**问题**：`memory` 模块（契约/领域/仓储/handler/算法）早已写好，但**全仓没有任何地方写它**：抽取只写 `profiles.document`；`tasks.scope_kind` 的 CHECK 只允许 5 种，**根本无法入队 memory 任务**；写入路径也没有任何重复检查，同句话会反复沉淀成多条。

**改动**：
- 迁移 `0024`：队列允许 `memory` 任务类型（handler 早就在册，只是永远排不上队）。
- 新增共享写入器 [memory-store.ts](../src/modules/memory/infrastructure/memory-store.ts)：统一 derive + 落库；**同作用域同类型下重复表述合并来源**（把新来源挂到既有记录上，不新增记录、不丢证据）；来源引用按作用域写入正确的来源类型（profile→interview_message / character→world_message / branch→world_event）。
- 访谈接线：提炼结果除写真实档案外，同时写入 `profile` 作用域记忆，来源=产生它的**真实访谈消息 id**，key 含类别；**不额外调用模型**。
- 修正/遗忘接口：`POST /api/v1/memory/records`（correct：旧记录 `superseded`、按用户措辞写入 `correction`；forget：置 `forgotten`，**不删除**），单一事务内同步生效；`GET` 列出记忆（默认只看 active，可按作用域过滤）。

## 二、修复并发安全加固迁移引入的生产回归（重要）

**症状**：并发执行者的 `0023_security_role_rls_hardening.sql` 执行了 `REVOKE ALL ON ALL FUNCTIONS ... FROM PUBLIC`，却没有把权限补回运行角色。量化结果（生产库实测）：`pl_app` 与 `pl_worker` **都无法执行** `check_fork()`、`immutable_snapshot()`、`validate_interview_question_messages()`、`validate_memory_candidate_*()`、`validate_memory_scope()` 等触发器函数，以及 `is_jsonb_string_array()`（CHECK 依赖）。触发器以**执行写入的角色**运行，因此新访谈提交、记忆候选写入、带不可变触发器的表写入都会在生产失败（"permission denied for function"）。

**改动**：迁移 `0025` 把**普通（非 SECURITY DEFINER）辅助函数**显式授予两个运行角色；租约与访客配额的 definer 函数保持最小授权不变。新增真实库守卫测试 `tests/integration/role-grants.test.ts`：遍历运行表上的所有触发器函数与 CHECK 辅助函数，断言两个角色都有 EXECUTE——**以后再撤销权限会直接让交付门槛失败**。

## 三、验证

- `npm run verify`：**152 项单元测试 + 21 项真实库测试**通过。新增 `tests/integration/memory-write.test.ts`：同句重复 → 1 条记录且保留两个来源；不同表述 → 2 条；纠正 → 旧记录 `superseded`、纠正记录 active；遗忘 → active 列表消失但行仍为 `forgotten`；跨 owner 隔离。
- 迁移 `0024`/`0025` 已应用于本地与**生产 Supabase**（`pl_migrations` 25 条）；生产库确认 `check_fork`/`immutable_snapshot`/`is_jsonb_string_array`/`validate_memory_scope` 对两个角色均为 `true`。
- **生产实测**：`GET /api/v1/memory/records` → 200；`POST` 遗忘一个不存在的记忆 → 修正后为 **404/NOT_FOUND**（此前是 503，已按 AUD-08 同类问题修正）。
