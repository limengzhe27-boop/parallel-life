# D-16 Phase 0 执行层：outbox 消费者与媒体链路接线（AUD-03）

负责人 dsh-main-20260923（主登记目录，单人执行并自审）。2026-09-24。状态：已完成并上线验证（M 与 W 两项有生产联动证据；H 项引用既有任务证据）。

## 问题（AUD-03 原文）

> 核对 W/H/M 入口与 outbox 消费者接线，逐项补真实联动证据。

核实结果：`outbox_jobs` **只写不读**（全仓只有 world 仓储在提交事务里写入），`worker-composition.ts` 只注册了 `interview/profile/world-build/memory` 四种 handler，`world`/`media` 两种任务**没有执行者**；用户说"发张照片"时 `resolveTurn` 也不会产生 `media.requested`。也就是说：图片这条链**从产生到执行全断**。

## 改动

| 部分 | 内容 |
|---|---|
| 迁移 [0022_outbox_consumer.sql](../db/migrations/0022_outbox_consumer.sql) | `outbox_jobs` 增加 `attempts` / `lease_until` / `last_error` 与领取索引；`claim_outbox_jobs(owner, max, lease)`（SECURITY DEFINER、**按 owner 作用域**、授予 `pl_app`——worker 角色刻意没有 tasks 的 INSERT 权限）；`finish_outbox_job(job, status, detail, task_id)`（授予 `pl_app` 与 `pl_worker`） |
| [dispatch-outbox.ts](../src/modules/tasks/application/dispatch-outbox.ts) | 派发策略：**job id 即幂等键**（崩溃/丢租约/客户端重试都不会重复入队）；无执行器或 payload 缺 requestId → 确定性原因**永久失败并记录原因**；内部/瞬时失败 → **重新入队**，受 `maxAttempts`（5）约束，超限才终止；一条失败不影响其余 job |
| [postgres-outbox.ts](../src/modules/tasks/infrastructure/postgres-outbox.ts) | 应用侧实现：`taskCommandId(jobId)` 由 job id 派生出确定性 uuid；payload 在**存储边界**解析（domain 保持无 zod 依赖）；`BUSY` 视为"已有活跃任务"，派发到既有任务而不是失败 |
| [media-handler.ts](../src/modules/media/infrastructure/media-handler.ts) | `media` handler：校验媒体请求确实存在，把 outbox job 标为 `NOT_IMPLEMENTED:media-adapter`，然后**如实失败**（M-01..M-03 未开发）；请求保持 pending，**绝不造假图** |
| [resolve-turn.ts](../src/modules/world/application/resolve-turn.ts) | 意图接线：`routeUserIntent` 判定为索图时，在**同一个回合事件**里追加 `media.requested`（此前索图静默什么都不发生） |
| [services.ts](../src/server/services.ts) + `POST /api/v1/outbox/drain` | owner 作用域的派发入口；世界消息路由在提交成功后自动派发该人生的 outbox（失败不影响已提交的回合，outbox 持久可再派） |
| [run-worker.ts](../src/modules/tasks/application/run-worker.ts) | 错误码保真：handler 自带的原因码（如 `UNAVAILABLE`）不再被折叠成 `AI_FAILED`（否则会去责怪一个**从未被调用**的模型） |

**顺带修复（生产抓到的真 bug）**：任务公共契约把媒体 scope 当 **uuid** 校验，而真实媒体请求 id 是效果作用域文本 id（`<eventId>_effect_<n>`）。首次上线后生产派发被拒、job 被标为永久失败——这是我自己的派发器造成的"持久但永不执行"的工作。已修：契约放宽为有界文本 id；内因失败改为有限重试；真实库测试改用真实形态 id，使这类契约错配在**交付门槛**上失败而不是漏到线上。

## 验证

- `npm run verify`：**134 项单元测试 + 18 项真实库测试**通过。新增：
  - `tests/outbox-dispatch.test.ts`（5 项）：索图派发恰好一次、无执行器拒绝并记录原因、缺 requestId 拒绝、内因失败重入队且不影响其余 job、超限终止、空 outbox 无操作。
  - `tests/integration/outbox.test.ts`：真实库端到端——提交含 `media.requested`（**效果作用域 id**）的回合 → outbox job 生成 → 派发**恰好一个** media 任务 → 二次派发不重复 → 无执行器 job 记为 failed + `NO_EXECUTOR` → 换 owner 无法领取。
  - `tests/turn-media-intent.test.ts`：索图回合必须带 `media.requested`，普通闲聊不产生媒体工作。
  - `tests/worker-outcome.test.ts`：handler 自带错误码保留、未分类失败仍为 `AI_FAILED`、取消为 `unknown`。
- 迁移 `0022` 已应用于**本地**与**生产 Supabase**（`pl_migrations` 22 条，两个函数在生产确认存在）。
- **生产实测（用户本人会话）**：
  1. 在世界 A 发"发一张窗外的照片给我看看" → `committed`，版本 6 → 7；
  2. 生产库出现媒体请求（prompt 为该句）与 `image.generate` outbox job；
  3. `POST /api/v1/outbox/drain` → `200 {claimed:1, submitted:1, rejected:0, requeued:0}`（修复后）；
  4. 库中出现 `scope_kind='media'` 的 queued 任务，job 记为 `submitted` 且 `provider_task_id` 指向该任务；
  5. `POST /api/v1/tasks/:id/run` 执行媒体任务 → 任务 `failed`，outbox job `failed`（`NOT_IMPLEMENTED:media-adapter`），媒体请求**仍待处理**，`assets` 计数 **0**（没有伪造图片）。
