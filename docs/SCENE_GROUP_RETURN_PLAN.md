# 现场、群聊、回归消息与按需媒体规划

日期：2026-10-08。状态：用户已授权按规划开发（2026-10-08）；具体实现仍按任务验收，不代表功能已上线。

唯一开发状态源为 DEVELOPMENT.md。本文件拆解需求和验收边界，不另建状态表。用户最新要求优先；保留语音暂缓、公共设定发布暂缓及多人后续范围。

## 一、此次确认与尚待确认

用户明确要求：单聊、群聊、现场分清；现场可由日程进入，也可有独立App；旁白交代时间、环境、动作和可观察事件；人物说话与旁白有区别；用户可输入话语和行动；现场图文按事件逐条出现而非固定背景加群聊；图片无需频繁生成，有成本，必要时出现，视频可后续加入；离开后回来应有具体吸引人的消息，不要求刻意隐藏秘密。

推荐首版以日程事件进入独立现场页面，先不新增桌面App；统一入口准备好后再增加独立App，二者共用现场记录。此入口顺序是本方案建议，不当作用户已最终选择。

现场不是即时3D操控，也不是几句话自动成功。首版是文字行动与图文事件反馈。多人NPC群聊与真人联机是不同能力，先做玩家+NPC，不能宣称多人玩家共享世界已完成。

## 二、现有能力核对

- src/features/phone/apps/messages.tsx 的“发起群聊”菜单目前仅 open('messages')，没有真实创建动作。当前世界消息以 actorId 表达私聊，没有群会话、成员变化、群消息历史、群上下文与群调度完整链路。
- 日程 participantIds 是约定参与人，不等于群成员，更不等于此刻现场在场人。
- 现有 narrative sceneDirection 是NPC创作提示，不是可玩的现场实体。
- 已有媒体请求与配额/结果状态基础，真实图生图、人物一致性、完整自动联动仍需验收；上传原图可用不代表生成图片可用。
- NAR-02R 已交辅助处理回归消息。不是另写一套离线导演，不承诺关闭网页时Vercel进程持续运行。当前先在进入/恢复时补算有界事件；外部推送后续另立任务。

## 三、三个体验边界

|形式|用户行为|内容及知情范围|
|---|---|---|
|单聊|手机向一个人发消息|对方发出的文字/图片；只能读取私聊及自己获知的信息|
|群聊|手机向明确群成员发消息|群内可见内容；发言不等于所有人同地点或执行了行动|
|现场|亲自在场说话或行动|环境、可观察动作、当面对白；不自动成为群/私聊消息|

同一事件可跨载体承接，不能互相冒充。私聊约见→群里协调→日程确认→到场参与→事后消息和作品。现场亲耳听见的话只对实际能听见的角色开放；私聊秘密不因一起到场而公开。需要转述时复用人物关系/来源机制。

## 四、现场页面与图文节奏

顶栏为事件名、返回手机；顶部一条可展开“当前事项”，展示当前目标、真实进展和限制，不塞长期任务清单。

主体为可回看的图文事件流：
1. 时间/地点标记：只在进入或明显变化时出现。
2. 旁白：无头像、无微信气泡，独立段落，用较柔和但可读的文字与留白，描述眼前动作/环境，不写NPC内心。
3. 角色对白：姓名或称呼明确、独立对白块/左侧细标记，正文对比更强；必要时小头像辅助识别，但不变成微信群聊。不能仅靠颜色区分，读屏保留“谁说”。
4. 用户行动：明确“你的行动”，与已发生反馈分开；输入不一定成功，未裁定时不展示为完成事实。
5. 图片：内嵌事件流，绑定其所呈现的已发生事件，可展开；不是有人发来照片，不造“刚刚拍好”台词。
6. 事件反馈：动作发生/未能发生、可观察后果、人物反应和当前事项变化。

底部统一自由输入，可说、做、或两者一起。少量可选建议帮助开始，不限制自由行动。未涉及的对象/事情不可凭点击就改变；查看分镜/回放等对象仅在确有可读内容时提供入口。

刷新恢复事件流、场景阶段和未发送草稿；返回手机保持当前现场，可继续，返回不等于完成。用户明确离开现场才产生离场行为，暂停/结束/退出网页须区别。首版同一玩家同一世界只参与一个当前现场，避免同时身在多处。

## 五、行动、事项与导演

创建世界或第一次触发相关事件时准备当前处境、可参与人物、环境限制、未了结事项和潜在发展，不固定最终结局。不重写整个访谈流程，但人生草案中应讨论想体验什么，形成可开始的处境，而不只给身份名称。

行动区分：查看、移动/操作、当面说话、尝试、计划/假设。用户说“如果我…”不当成行动；说“我想获得奖项”不立刻发奖；“让他答应”不替NPC作决定。组合行动可以分步反馈，执行到关键未知/新选择时停下。

导演提出环境/事件变化并选择必要角色；NPC按自己的目标、人设、关系和可见信息反应；运行时验证人物是否在场/能听见、行为是否合理、资源是否满足、时间与已发生事实是否冲突，再提交。不能借现场绕过事务、幂等、来源及权限边界。

事项至少区分未开始/进行中/受阻/完成/放弃，完成须有事件依据。用户自述已完成仍保留自述来源，不转成独立验证；现场经过裁定的结果可作为世界内部结果，并不证明现实行为完成。只对相关事项产生影响，不是所有任务一起更新。展示主要事项+少量相关事项；形成阶段结果后留出休息，不不断追加强制困难。

完整长期任务体系仍待讨论，本期只支持当前事件事项，避免借UI承诺完整玩法已经设计完毕。

## 六、群聊首版

- 用户选已有NPC创建群，保存群名、成员、创建来源；导演也可因具体共同事件提出群/创建有来源的群，用户可离开。成员实际存在于本世界，不能跨分支混用。
- 列表包含单聊和群聊，但标题、头像与成员入口明确区别。支持群历史、未读、图片附件、成员查看、退出和恢复；首版不扩展红包、语音、通话。
- 普通发言通常由最相关一人回应，必要时第二人补充或反对；建议首版每次最多两名NPC回应，作为可调成本/噪声上限，不要求必须两人。
- 明确@优先相关人，不等于强制所有被@的人立刻答。其余人可保持沉默；有依据时导演安排稍后的跟进，不伪造每条消息实时在线。
- 群内产生承诺或邀请，仍需按已有规则确认；消息不是执行行为的唯一凭证。群消息不能自动泄露私聊。
- 新加入的人默认只见加入后信息；若需要获知早先内容，用有来源的显式转述。历史UI与模型读取遵循同一规则。退群后的新消息不继续交给该NPC。
- 群附件与相册引用同一授权素材；群聊天不是现场，群成员不是在场名单。

## 七、回归消息

NAR-02R先优化现有链路：根据上次未了结事情、角色目标、离开时长和已保存状态，呈现具体世界进展/机会/关系变化/行动结果。不是默认隐瞒，不是每次灾难，不把没登录当成故意失约。

锁屏少量重点消息，推荐一件主要变化和一两条关联信息，具体阈值由现有冷却/补算规则验证。消息时间体现发生顺序，不能都变成回来时的“刚刚”；如果恢复时才计算事件，应诚实记录系统生成/提交时间与推演的故事发生时间，不伪称一直后台模拟。

重大主人公选择保留给玩家；过期事件显示后续，不拿已解决的危机继续催。点通知直达对应单聊/群聊/事件邀请。场景只在用户进入后呈现其现场视角，不在锁屏提前泄露全局秘密。

## 八、媒体成本与真实性

文字是完整可用的基础。图片仅在建立新地点/重要人物到场或环境变化/关键行动可视化/具体成果或用户明确要求时评估；普通对白、轻微移动、同一场景重复不自动生成。

先裁定并保存事件，再提出媒体请求。建议首版单次事件推进最多自动申请一张静态图；相同场景与已发生事件、人物参考和构图要求一致时复用已有素材。不同事件不可拿旧图冒充新证据；复用环境图要明确只是场景参考。

导演提出需要图不代表必须生成。运行时结合账号/世界预算、冷却、已有素材和在途请求决定允许/复用/只用文字。具体单价、次数/金额额度与服务质量待实际供应商验证，不预先承诺免费或统一频率。

请求有固定业务标识、来源事件、人物参考版本与用途，防刷新/重复提交/超时导致重复收费。unknown不自动重新付费；失败显示正文可继续，用户显式重试。照片尚未成功不得说“照片发给你了”。图片晚到不改写原叙事结论，不覆盖旧人物资料。

普通头像仅用于展示，不默认做人物图生图。已授权的参考图与角色形象需核实一致性，图片与角色绑定不扩大到所有世界。NPC发照片与现场配图是不同用途，只有有实际分享事件的图才进入消息；是否成为相册照片也要有作品/照片依据，不能把每幅旁白插图都当相机拍下的照片。

视频在图文闭环完成后做小规模验证：关键已发生片段、用户主动请求，默认关闭自动视频；单独验证成本/时延/身份一致性，不让预生成视频替用户选择下一步。视频失败不阻塞文字；语音仍暂缓。

## 十、验收样例与待确认

共同样例：第一次试拍。玩家先私聊摄影师，群里确认安排，日程确认后进入现场。分别尝试改走位与拆镜头，比较动作、人物态度、事项和后续手机内容。过程中图片预算耗尽，文字仍能完成。重进不会再收费或重复推进。离开数天后看到相关后续，不替玩家完成试拍或强制失约。

其他身份样例需覆盖非工作关系场景，防止只对导演身份成立。群秘密、退群、现场听见范围与跨世界均有反例；自由行动不会因为用户一句话自动获得大奖/改变NPC身份。

已采用首批日程入口、文字现场与按需图片的开发顺序。实现前需收敛：现场故事时间的推进/暂停与原1:1规则如何协调；图片具体额度与服务质量；是否需要首版群历史完整显示（本建议新成员加入后范围）；长期任务框架与公开设定创作仍单独讨论。没有增长/留存实测，不声称该呈现已证明更好玩。

## 十一、2026-10-08 新要求与待讨论规则

已确定：用户进入世界后，不再通过导演Agent对话修改当前分支。导演保留为内部调度者；玩家通过消息、现场言语和行动改变发展。审查移除旧“与导演讨论剧情”及改设定入口，保留人生切换、存档和既有时间管理；不能混同为删除幕后导演，也不静默改写已有历史。NPC幕后活动只展开与主角当前或潜在经历有关的事情，仍受人设、关系和信息来源约束。

以下是主Agent建议，尚需讨论与体验验证，不当作已确认实现：

1. 创建只确认公开起点：身份、地点时代、体验主题、明确指定的人和带入资料。已知人物只展示玩家身份本应知道的内容；隐藏动机、未知关系、未来事件与结局不提前发给客户端。选择起点不等于控制他人结果。
2. 先提供少量官方可体验起点，帮助用户获得灵感，不固定结局；与暂缓的公开投稿/社区发布分开，不恢复LIB-04B在途界面或宣称目录已完成。
3. 前台建议“长期目标／短期任务／当前情况”，情况是描述，不是可勾选任务。“眼前事件”不作为并列分类。底层CurrentMatter只是当前事项证据模型，不是完整任务引擎。建议突出一个主要短期任务，加零到两个可选任务，这是体验假设而非已确定上限；只有有因果关联的任务随行动变化。
4. 统一输入，不强制选消息或行动。私聊/群聊首先是通信；现场可自由输入对白和行为，区分计划、假设、尝试；重要歧义才简短澄清。表达愿望不等于行动成功。
5. 回归须有时间和状态变化，是否现实1:1仍未决定。本批保留既有时钟/暂停语义，不擅自重写全局日期。后续验证少量相关进展、长过程压缩、重要选择留给玩家；手机各应用同一故事时间。
6. 回馈包括有来源的结果、关系行为变化、新的可行行动、身份成长、持续记忆与阶段满足。不能只用消息数、好感数字或无限追加困难充当好玩；失败说明原因与可能办法，不强行将每次失败都包装成奖励。

后续以至少两个完整体验样例验证：用户是否知道能做什么，行动是否有区别，后果是否看得见，休息后是否有理由回来。没有留存实测，不写成已经有效的玩法。

2026-10-09用户修正：预设须是较完整可体验剧本，不只是起点；前台不使用生硬“长期目标”，用身份本人的自然记录表达；离开有少量合理进展，消息跨日期保存，iPhone锁屏按会话折叠真实历史；统一输入可用但识别须做好；反馈方向采用。细则与待定事件顺序见PRESET_SCRIPT_AND_RETURN_SPEC.md，后续内容优先于本文件旧“只做起点”建议。群/现场/原NPC链路继续开发，公共发布模块不因此直接开放。
